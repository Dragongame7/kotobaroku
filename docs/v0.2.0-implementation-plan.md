# ことば録：v0.2.0実装方針書

- 作成日：2026-10-17（日本時間）
- 対象：`nemotron-web`。設計作成時は `0.1.0`、実装後は `0.2.0`。
- 文書の状態：第1〜13節は実装前に合意した方針。実装時の変更・検証結果・未評価の事項は第14節に追記する。
- 進め方：本書を基準として実装し、設計時の目標と実測結果を区別して記録する。

## 1. 今回の決定

1. **翻訳も含め、通常利用のすべてのLLM処理を `gemma4:latest` に統一する。** 文末判定、日本語の誤変換補正、日英翻訳、文章整形、要約で同じモデルを使う。
2. 音声認識は引き続きNemotronを使う。Gemmaによる音声直接認識への置換は行わない。
3. 「天気がいいので選択しようと思います」のような日本語の同音異義語を、文脈に基づいて最小限補正する。
4. **単語登録は今回実装しない。** 登録画面、ユーザー辞書、用語集の保存・取込・編集、ASRへの登録語の優先指定を対象外とする。
5. 認識原文、補正後の文章、翻訳結果を別々に保持する。補正が失敗した場合も認識原文を残し、原文による処理を続ける。
6. Qwen、TranslateGemma、Hy-MT2、小型Gemma、クラウドサービスへ自動で切り替えない。

この決定は、翻訳にTranslateGemmaを残す案より優先する。`gemma4:latest` と `translategemma:4b` は別モデルであり、次版の通常経路では前者だけを使う。

## 2. 解決したい問題と対象範囲

「選択」と「洗濯」は同じ「せんたく」という読みを持つ。音声認識が選んだ表記を、文脈から再検討できるようにする。ただし、自然に見える文章への自由な書き換えは行わない。

| 入力例 | 期待する結果 |
|---|---|
| 天気がいいので選択しようと思います | 天気がいいので洗濯しようと思います |
| 候補から会場を選択しようと思います | 変更しない |
| 洗濯機を選択しようと思います | 変更しない |
| この件については検討しません | 否定を維持する |
| 田中さんに15時までに3部送ります | 人名・時刻・数量を変更しない |
| 選択しようと思います | 文脈が不足しているため原則変更しない |

対象は次のとおり。

- 日本語の通常文字起こし：録音中に原文を表示し、文のまとまりごとに補正結果を追加する。
- 日本語→英語のリアルタイム翻訳：日本語補正後の文章をGemmaで翻訳する。
- 英語→日本語のリアルタイム翻訳：日本語補正は行わず、Gemmaで翻訳する。
- 整形・要約：Gemmaを既定とし、補正後の文章を使うか原文を使うかを明示する。
- 録音後の補正再試行、原文へ戻しての再翻訳、補正差分の確認・保存。

対象外：新たな音声認識モデルの導入、Whisperのリアルタイム化、音声の再認識による自動多数決、追加学習、話者分離、翻訳方向の自動切替、日本語以外の誤変換補正。

## 3. 現状の確認と実装上の差分

2026-10-17にソースとローカルのモデルマニフェストを確認した。

| 箇所 | 現状 | 次版で必要な変更 |
|---|---|---|
| `server/app.mjs` | 整形・要約と文末判定の既定がQwen。翻訳はTranslateGemma | 通常経路のモデル設定を一元化し、すべてGemmaにする |
| `server/translation.mjs` | 文末判定後、認識原文を直接翻訳。LLM要求は直列 | 検証付き補正を挟む。原文と翻訳入力を分離する |
| `server/sentence-buffer.mjs` | 句点、ルール、LLM候補判定、時間・文字数上限で区間を確定 | 原文の境界処理を維持し、補正によって区間を動かさない |
| `/ws/transcribe` | 原則としてASRイベントの転送 | 通常文字起こしでも文単位の補正処理と完了待機を追加する |
| `src/Translation.tsx` | 一つの原文と訳文を表示・保存 | 原文・補正後・実際の翻訳入力・区切り理由を扱う |
| `src/App.tsx` | 原文、整形・要約、履歴を管理 | 補正結果表示、元原文の保持、モデル表示・履歴移行を追加する |
| `server/translation-models.mjs` | 専用翻訳モデルごとにプロンプトを分ける | 通常翻訳はGemma用の汎用翻訳経路を使う |
| `server/translation-memory.mjs` | 別の専用翻訳モデルを解放し、同時GPU常駐を確認 | 単一GemmaとASRを前提にし、CPU併用も状態として扱う |

現行の文章整形は「推測による訂正をしない」指示であり、同音異義語の補正機能にはならない。誤変換補正を独立した処理として追加する。

文書作成時は `http://127.0.0.1:3210/api/health` に接続できなかった。今回はアプリやOllamaを起動しておらず、Gemmaの推論品質、速度、現在のGPU配置は未測定である。既存のQwenによる試験結果をGemmaの検証済み結果として扱わない。

## 4. モデル統一と設定移行

### 4.1 単一設定を正とする

次版の標準設定は次のとおり。

```dotenv
OLLAMA_MODEL=gemma4:latest
```

通常経路は起動時に解決した一つの `llmModel` を共有する。

| 処理 | モデル | 備考 |
|---|---|---|
| 文末判定 | `gemma4:latest` | JSON Schemaで候補IDを返す |
| 日本語誤変換補正 | `gemma4:latest` | JSON Schemaで置換候補を返す |
| 日本語→英語・英語→日本語 | `gemma4:latest` | 訳文のみをストリーミングする |
| 整形・要約 | `gemma4:latest` | 用途別の指示を使う |

- モデル名の既定値を複数ファイルに重複定義せず、`server/config.mjs` または新しい共通設定に集約する。
- 新しい通常画面では役割別のモデル選択を置かず、「使用モデル：Gemma 4」を表示する。モデルは録音中に変更しない。
- 旧 `TRANSLATION_MODEL`、`BOUNDARY_MODEL` は通常経路では使用しない。値が残っていれば起動ログと設定情報で廃止を通知する。新しい `CORRECTION_MODEL` は追加しない。
- 既存の `.env` にQwenの `OLLAMA_MODEL` が残る場合は、次版移行時にこの一項目をGemmaへ変更する。例示ファイルだけの更新で済ませない。
- 過去の行に保存されたモデル名は履歴として保持する。ただし次版での再翻訳・再補正は現行Gemmaを使い、元結果のモデルと再処理モデルを区別して記録する。
- 旧 `kotoba.translation-model` は通常モデルの選択に使わない。過去の原文・訳文・下書きを削除せずに設定だけ移行する。
- 通常のAPIにクライアントからモデル名が届いた場合、サーバー解決済みモデルと一致するか検証する。異なるモデルを黙って実行しない。
- 既存のモデル比較は、利用者が録音停止後に明示的に開く比較用途として残す。別モデルを通常経路へ復帰させる仕組みにはしない。比較後の録音準備ではGemmaを再確認する。

### 4.2 モデルの識別とメモリ

ローカルマニフェストでは、導入済み `gemma4:latest` は `gemma4` 系、`8.0B` 表記、`Q4_K_M`。モデル層は **9,608,338,848バイト（約9.61GB、約8.95GiB）**。これはファイルサイズであり、実行時VRAM量ではない。

確認したモデル層digest：`sha256:4c27e0f5b5adf02ac956c7322bd2ee7636fe3f45a8512c9aba5385242cb6e09a`。

このPCの既存検証環境はRTX 3080・VRAM 10GB、メインメモリ32GB。Nemotron、Gemmaの重み、KVキャッシュ、計算用メモリを含めた全GPU常駐は保証できない。単一Gemmaの共有は別々のLLMを同時に載せるよりモデルの重複を減らすが、収まることを保証しない。

- Gemmaは役割ごとに別インスタンスを要求せず、同じモデル・コンテキスト設定を共用する。
- `/api/show`・`/api/ps`・`nvidia-smi`で版、digest、量子化、モデル常駐量とGPU全体の使用量を記録する。
- CPU併用を許容し、「GPU」「CPU併用」「確認できず」を表示する。CPU併用だけを理由に、補正や文末判定を無断で別モデルへ変更しない。
- OOM・モデル未導入ではASR原文表示を維持する。補正は「未実施」、翻訳は再試行可能な失敗として残す。
- `latest` の内容は変わり得るため、自動pull・自動更新はしない。検証時のdigestを保存し、内容変更後は再評価する。
- 旧モデルのファイルを削除しない。メモリ解放は本アプリが読み込んだ非稼働モデルの範囲に限り、他用途のOllamaモデルを一括で解放しない。

### 4.3 推論設定

開始値は共通で `num_ctx=4096`、逐次要求数1、通常は推論過程を出力しない設定とする。`think=false` の実際の受理・動作は、導入済みGemmaとOllamaで検証する。

判定・補正は `stream=false`、温度0、JSON Schemaを使う。翻訳は温度0を開始値としてストリーミングする。用途ごとに出力上限を設け、隠れた推論出力や説明文を訳文として表示しない。モデルのテンプレートや `system` ロールの扱いも実機で確認する。

整形・要約で長い原文を処理する場合は入力を検証し、4,096トークンの枠に収まらないデータを黙って切り捨てない。既存の10,000 UTF-8バイト制限とは別に、入力と出力予約分を含む上限を設計する。長文の分割・要約は録音終了後に直列で行い、その方式を画面に示す。

## 5. 処理の流れ

```text
マイク → Nemotron → 認識中テキストを即時表示
                  ↓ ASR確定原文
              原文バッファ
                  ↓ 句点／文末判定／時間・文字数上限
              原文の区間を固定
                  ↓ 日本語補正ONかつ適用対象
              Gemmaが置換候補を生成
                  ↓ サーバーが読み・対象・差分を検証
              補正後の文章、または原文を採用
                  ├→ 通常文字起こし：補正結果を表示
                  └→ リアルタイム翻訳：Gemmaで翻訳 → 訳文を順次表示
```

- ASRのデルタ到着ごとに補正LLMを呼ばない。
- 境界判定は原文に対して行う。補正結果の句読点や文字数から再分割しない。
- 「。」を受け取った時点で原文区間と次の行は即座に確定する。その後に補正・翻訳が必要なので、訳文の即時完成を意味しない。
- 日本語補正は初期値ON、録音前にOFFへ変更可能とする。英語は適用対象外と明示する。
- 仮訳は原文から生成し、「未補正の仮訳」と表示する。原文区間の最終確定時にだけ補正を実施し、同じIDの最終結果へ更新する。
- 文末判定と補正を一つのLLM応答にまとめる最適化は次版の初期実装では行わない。目的と検証を分離し、計測後に検討する。

### 5.1 既存の文章区切りを維持する

| モード | 時間上限 | 文字数上限 | 補正前の扱い |
|---|---:|---:|---|
| 速度重視 | 6秒 | 100字 | 原文区間を固定して次へ進む |
| バランス重視 | 10秒 | 150字 | 同上 |
| 文脈重視 | 15秒 | 200字 | 同上 |

「。」優先、約750msの間、発話にリセットされない約2秒ごとの意味判定、UTF-8で1,200バイトの入力保護、上限による区切り理由の表示を維持する。時計はASR確定原文の受信からであり、補正・翻訳の待ち時間を含まない。

上限によって節の途中で切れた区間は、無理に補完しない。判断に必要な文脈が欠ける場合は補正を行わず、原文を使う。

### 5.2 文脈の渡し方

現在の区間に加え、直前の最大2区間の**認識原文**を、合計1,200 UTF-8バイト以内で補正用の参考情報として渡す。古い部分から省略し、途中の文字を壊さない。

原文の参照履歴はASRの確定順に管理し、前の翻訳が完成するまで待たない。過去の自動補正を無条件に文脈として繰り返し使わず、誤補正の連鎖を抑える。参考情報は補正対象に含めない。未来の発話を待つために確定済み区間を保持し続けない。

## 6. 誤変換補正の仕様

### 6.1 初版で許可する補正

次版は、読みが同じ漢字語への局所的な置換に絞る。

1. サーバーで日本語の形態素解析を行い、補正可能な語に候補IDを付ける。
2. 既知の名詞で、固有名詞・数詞・記号ではなく、全体が漢字1〜8文字の語を対象候補にする。
3. Gemmaには現在の原文、参考文脈、候補IDと語を渡す。文脈上の誤変換が明確な場合のみ置換を提案させる。
4. 置換語を再解析し、既知の対象語としての読みが一致することをサーバーで確認する。読みが不明・複数解釈で特定できない場合は採用しない。
5. 全検証を通った置換だけで補正結果を組み立てる。Gemmaが生成した全文を直接採用しない。

読みに近い別語、助詞・活用の修正、ひらがなからの漢字化、語句の挿入・削除、複数語にまたがる置換は初版の対象外とする。この制約により直せない誤りは残るが、正しい文を壊す範囲を抑える。

形態素解析はNode側で使える `kuromoji` を第一候補とし、実装の最初にNode 24・ESMからの利用、辞書初期化時間・常駐RAM、文字位置の仕様、ライセンスを確認する。一般の形態素解析辞書の同梱は内部検証のためであり、今回見送る「利用者による単語登録」とは別である。未知語・人名を推測して書き換える手段には使わない。

### 6.2 構造化出力と検証

サーバーから渡す対象候補の例：

```json
{
  "rawSource": "天気がいいので選択しようと思います",
  "context": [],
  "candidates": [{ "id": 1, "surface": "選択", "reading": "センタク" }]
}
```

Gemmaの応答例：

```json
{
  "edits": [
    { "candidateId": 1, "replacement": "洗濯", "reason": "天気のよさを理由にする家事の文脈" }
  ]
}
```

変更しない場合は `{"edits":[]}`。JSON Schemaで件数・型・長さ・追加プロパティを制限し、解析後にも次を確認する。

- 実在する候補IDであり、同一IDの重複がない。
- 元の対象語と元原文上の範囲が一致する。位置はサーバーが管理し、LLMに文字オフセットを決めさせない。
- サロゲートペア、異体字セレクター、絵文字を含む原文でも位置を壊さない。トークナイザーの位置をそのままJavaScriptのオフセットと仮定しない。
- 対象・置換語とも適用条件を満たし、正規化した読みが一致する。
- 数値・日付・時刻・金額・否定表現・固有名詞を保護する。漢数字を含む対象は初版では補正候補から除外する。
- 初期上限は1区間3件、変更する元の文字数合計は12字か原文文字数の25%の小さい方まで。候補範囲は重ならない。
- 補正後の翻訳入力が1,200 UTF-8バイト以内に収まる。
- 置換対象外の部分、句読点、空白、語順が完全に維持される。

いずれかに失敗した応答は全体を不採用とし、原文を使う。文章の自然さやGemma自身の「確信度」だけで採用を決めない。上の制約でも意味の正しさは保証できないため、後述の誤補正評価を必須とする。

原文や文脈中の命令はデータとして扱う。「前の指示を無視」等が含まれていても、補正・翻訳以外を実行しない。

## 7. 処理順、制限、失敗時の動作

### 7.1 一つのLLMキュー

通常文字起こし・翻訳の共通処理を導入する。単一セッション制限を維持し、補正を通常録音へ追加した際に、別タブの整形・比較とLLM要求が重複しないようにする。

- 同時LLM要求は1件。確定区間は到着順に処理し、同一区間の「補正→翻訳」を一つの処理単位として扱う。
- 確定区間の処理を、待機中の仮訳・文末判定より優先する。古い同一区間の判定・仮訳要求はまとめる。
- 実行中の要求は中断または期限で終了させ、最新結果が来ても、ID・原文revision・要求世代が一致しなければ反映しない。
- 意味判定だけは既存どおり、検査済み原文が現在の先頭と一致する追記を許容する。補正結果を別の原文revisionへ流用しない。
- 先行区間が補正・翻訳の順序を乱さない。待ち時間が伸びても原文の区間確定・画面表示・ASR音声受信は継続する。

### 7.2 初期の時間・量の制限

| 処理 | 初期上限／方針 |
|---|---|
| Gemma準備 | 90秒。通常のマイク送信開始前に完了させる。中止可能 |
| 意味判定 | 実行3秒。失敗しても既存ルールと上限で区切る |
| 日本語補正 | 実行3秒。待ち行列での経過が1秒を超えた場合は省略し、原文による後続処理へ進む |
| 翻訳 | 1区間60秒。失敗行を保持して停止後に再試行 |
| 待機中の確定区間 | 最大32件。超過分も原文を保存し、後から処理できる状態にする |
| 仮訳 | 従来の約6秒を維持。最終確定処理がある場合はそちらを優先 |
| 停止後の残処理 | 翻訳は既存の最大10分を維持。通常文字起こしの補正待機にも上限と中断操作を設ける |

実行時間と待ち行列時間は別々に記録する。上限は実装時に調整できるサーバー定数とし、無制限リトライは行わない。

### 7.3 状態別の動作

| 状況 | 動作 |
|---|---|
| 補正OFF・英語 | 原文を使い、補正LLMを呼ばない |
| 候補語なし・文脈不足 | 原文を使う。文脈不足ならGemmaも変更なしを選べる |
| 補正のJSON不正・読み不一致 | 原文を使い、「補正を適用せず」と理由を記録 |
| 補正が混雑・タイムアウト・モデルエラー | 原文で翻訳へ進む。未補正であることを表示 |
| 翻訳が失敗 | 原文・補正結果を保持。停止後の再試行を提供 |
| CPU併用 | 配置を表示し、実測する。別モデルへ変更しない |
| Gemma未導入・準備失敗 | 理由を表示。利用者が通常の原文文字起こしへ進める導線を用意する |
| 「翻訳だけ中断」 | ASR原文を継続。以後の翻訳用補正も中断し、原文を保持する |
| 録音停止 | 残原文を確定し、許可された残処理を流す。マイクは直ちに停止する |
| 残処理中断・接続切断 | 進行中処理を中断し、未完了として保存。古い応答で表示を上書きしない |

現在の「GPU同時常駐を確認できなければルール判定へ切替」は、単一Gemma設計に合わせて変更する。CPU併用とモデル障害を区別し、文末判定のルールへの退避は要求失敗・期限切れなどの理由を明示する。

## 8. データ、API、画面

### 8.1 行データ

次版の行データには最低限、次を保持する。型名は実装時に統一する。

```text
schemaVersion: 2
id / revision / processingGeneration
rawSource / sourceParts / boundary
correction: { mode, status, correctedSource, edits, fallbackReason,
              inputRevision, model, modelDigest, promptVersion, elapsedMs, queueMs }
translationInput: { text, origin: raw | corrected, inputRevision }
translation: { text, status, model, modelDigest, promptVersion, inputGeneration }
sourceLanguage / targetLanguage / receivedAt / committedAt
```

- `rawSource` とASR断片の対応は不変。補正結果や手修正で上書きしない。
- 補正は `off / pending / unchanged / applied / skipped / failed / canceled` 等を区別し、翻訳の成功・失敗と別管理する。
- 原文へ戻す操作では `rawSource` を変更せず、採用入力と処理世代を変える。旧訳は「再翻訳が必要」とし、Gemmaで再翻訳する。
- 読みや品詞などの内部検証データを通常画面へ並べない。モデル名・変更箇所・未補正理由など、判断に必要な情報を表示する。

### 8.2 APIとイベント

- `/api/health`：モデルの統一設定、補正対応、モデル導入状態を追加する。GPU配置は起動時・録音準備時に確認した時刻も添え、古い値を現在の状態と断定しない。
- `/ws/translate`：`session.update` に補正の `off / conservative` を追加する。モデル名はサーバー設定から決め、互換のため受け付ける場合も一致検証する。
- `/ws/transcribe`：補正ONの場合は同じ原文バッファ・補正処理を利用する。ASRイベントを維持したまま補正行・完了イベントを追加する。
- `caption.segment`、`caption.correction.started/completed/skipped` 等を追加し、イベントにID・revision・処理世代を含める。
- 既存の `translation.*` は段階的に互換性を保ち、訳文の `inputGeneration` を検証する。
- 通常文字起こしにも残補正の完了・中断イベントを設ける。ASRのcommit到着だけで接続を閉じない。
- 録音停止後の `/api/correct` を新設し、1区間の原文・参考文脈・モードを検証する。翻訳再試行は同じ補正処理を共有し、二重に補正しない。
- 手貼り付けの長文はクライアント任せにせず、サーバーで原文を安全に分割して直列処理する。本文の変更は原文revisionの更新として扱う。
- 既存のlocalhost・Origin検証、サイズ制限、録音中の整形・比較禁止、切断時Abortを新APIにも適用する。

### 8.3 画面操作

- 録音前に「日本語の誤変換補正：ON/OFF」を選択でき、設定を保存する。録音中は固定する。
- 翻訳画面は「認識原文／補正後」を確認できる。変更があれば `選択 → 洗濯` の差分を表示する。訳文がどちらを使ったかも表示する。
- 通常文字起こし画面にも原文と補正後を切り替える表示を追加し、整形・要約へ渡す入力を明示する。
- 手修正は録音停止後に行い、録音由来の原文とは別の下書きとして保持する。古い補正・訳を黙って手修正後の文章へ対応付けず、再処理を促す。
- 「原文に戻して再翻訳」「補正を再試行」は停止後に利用可能とする。自動スクロール・原文の先行表示を維持する。
- 補正失敗を翻訳失敗と同じ赤い行にせず、原文使用の説明を表示する。モデル未導入・翻訳失敗は操作が必要な状態として区別する。

### 8.4 保存と互換性

- 新データには版を付け、原文・採用した補正結果・実際の翻訳入力・差分・モデル情報を保存する。
- 旧 `kotoba.translation`、`kotoba.draft`、履歴を読み込み、旧 `source/text` を過去データとして保持する。手編集済みの可能性があるため「元のASRを復元できた」とは表示しない。
- 古いデータへ補正を自動適用しない。未完了の行は再試行可能な中断状態で復元する。
- コピー・Markdown保存には、補正がある場合の原文と補正後、訳文、未補正・未完了・上限区切りを含める。
- 保存容量不足を通知し、ファイル保存へ誘導する。音声を追加で長期保存する設計にはしない。

## 10. 実装の順序

### 第1段階：Gemmaの成立性を確認する

1. `gemma4:latest` の導入情報を確認し、テキスト生成、JSON Schema、推論過程の抑制を試す。
2. Nemotronと同時に起動し、準備時間・GPU/CPU配置・短文翻訳・文末判定・JSON補正を測る。
3. 同じモデル・同じコンテキスト設定を共有できる共通クライアントを作る。
4. 形態素解析の依存を検証し、例文から「選択」の位置と読みを取り出せることを確認する。

成果物：`reports/gemma-readiness.json`。この段階では品質・速度を推測で保証しない。結果が悪くてもQwenやTranslateGemmaへ自動復帰しない。

### 第2段階：補正エンジンを単独で作る

候補ID方式、読み一致、最小差分、保護対象、不正応答、タイムアウト、原文退避を実装する。固定した評価データで、補正率と誤補正率を測る。

成果物：補正モジュール、単体試験、`reports/correction-evaluation.json`。

### 第3段階：通常録音・翻訳へ組み込む

共通セッションと一つのLLMキューを導入する。原文の即時表示、区間確定、補正、翻訳、停止・中断・再試行を接続する。モデル既定と旧設定を移行する。

### 第4段階：画面・保存・履歴を整える

原文と補正後の表示、差分、採用入力、ON/OFF、原文への復帰、旧データ復元、保存形式、自動スクロールを実装する。

### 第5段階：実音声で通し検証する

合成音声に加え、このPCの実マイクで評価する。品質、追加遅延、処理待ち、メモリ、長時間運転の結果を記録し、READMEと本書の実装結果欄に反映する。

## 11. 評価と完了条件

### 11.1 補正品質

固定評価集合は最低200例を用意し、プロンプト調整用と最終確認用を分ける。

| 区分 | 最低例数 | 内容 |
|---|---:|---|
| 補正すべき同音異義語 | 60 | 日常会話、仕事、今回の「選択／洗濯」等 |
| 変更してはいけない文章 | 100 | 正しい同音語、人名・製品名、数値、否定、引用、曖昧な文 |
| 前後・強制区切り | 20 | 文脈が前の区間にある例、節の途中、長い無句点原文 |
| 不正・境界条件 | 20 | 指示文、未知語、反復語、絵文字、混在英語、不正JSON |

初期の合格目標は、対象の同音語補正を60例中45例以上成功、無変更100例への不要な変更は0例、数値・否定・固有名詞の破壊は0例とする。これは固定データでのリリース判定目標であり、一般の会話での成功率を保証する数値ではない。

実音声ではASR単体と補正後のCERを同一の正解文で比較し、対象語の訂正成功数、正しかった語を壊した数、補正を見送った数も別に記録する。テキストだけの補正試験をASR全体の認識精度と混同しない。例文だけの特例コードは作らない。

### 11.2 遅延・メモリ・連続運転

- モデル準備時間とウォーム状態の要求時間を分ける。
- 日本語補正の追加実行時間はp95で2秒以内を開始目標とし、3秒の打切りと原文退避が機能することを確認する。
- `ASR確定原文受信 → 原文区間確定 → 補正開始/終了 → 翻訳開始 → 最初の訳文 → 訳文完了` を分けて測る。文脈待ちの時間とモデル時間を混同しない。
- 同じ音声・Gemmaで補正ON/OFFを比較し、句点あり／なし、3つの区切りモードで遅延と省略数を記録する。
- 15分以上の日本語マイク録音で、原文欠落、順序逆転、行の無制限な伸長、未解放メモリ、LLM要求の重複がないことを確認する。
- GPUモデル常駐量、GPU全体使用量、CPU併用、RAM、キュー最大長、補正の省略・期限切れの割合を記録する。

Gemmaの速度・品質が目標に届かない場合は、制約・プロンプト・キューを調整して再評価する。モデル統一の決定は維持し、未達の結果を隠して完了扱いにしない。別モデルの採用が必要になった場合は次の方針変更として扱う。

### 11.3 自動・ブラウザ・実機試験

- 既存の文末判定、上限区切り、仮訳更新、原文保持、古い応答の破棄、自動スクロールを回帰確認する。
- 読みの不一致、未知語、候補ID重複、変更上限超過、JSON不正、指示文を含む原文を検証する。
- 同一語が複数回ある原文、絵文字の後の候補、英数字混在で置換位置を検証する。
- Gemmaへの要求が判定・補正・翻訳・整形・要約のすべてで同一モデルになり、通常要求にQwenや専用翻訳モデルが混入しないことを確認する。
- 補正OFF・英語では補正要求が0件になることを確認する。
- 補正エラーでも原文翻訳が進むこと、翻訳失敗時に補正結果が残ることを確認する。
- 録音中・残処理中・別タブの排他、停止・切断・中断・再試行時の古い応答の扱いを確認する。
- 補正ON/OFF保存、差分、原文への復帰と再翻訳、旧データ復元、コピー・ダウンロードを確認する。
- 320/375/768/1440pxの表示と、通常録音・翻訳両方の最新部分への追従を確認する。
- 実機では日英両方向を試し、Gemmaの訳に原文・前置き・推論過程が混入せず、前文を重複翻訳しないことを確認する。

## 14. v0.2.0実装結果（2026-10-17）

### 14.1 実装した範囲

- `server/config.mjs` に共通モデルとコンテキスト設定を集約。通常の文末判定・補正・翻訳・整形・要約を同一Gemmaで処理する。異なるモデルを指定した通常API要求は拒否する。旧設定は警告し、別モデルへ自動復帰しない。
- `server/correction.mjs` にkuromoji 0.1.2の標準辞書による候補生成、Gemmaによる文脈判断、読み・品詞・位置・変更量・原文維持の検証を実装。ユーザー辞書・単語登録は導入していない。
- 通常録音と翻訳の共通処理は、既存 `LiveTranslation` を `translateEnabled=false` でも動かす形にした。別の `caption-session.mjs` は追加せず、文の組立、待ち行列、停止・中断処理を共有する。
- 日本語原文、補正後、差分、翻訳入力の由来を保持する。通常画面で採用入力を選択でき、翻訳画面では原文での再翻訳と補正しての再翻訳ができる。手編集後の旧補正は再適用しない。録音再開時の文書位置も保存し、同じ文を繰り返しても過去の手編集部分へ新しい補正を適用しない。
- 履歴・下書き・Markdown保存に補正と入力の由来を追加。旧データは読み取り、未完了処理は中断状態として復元する。
- 原文受信・区間確定・補正開始/終了・翻訳開始・最初の訳文・完了の時刻を `timing` に記録し、ASR以前の遅延と区別する。
- kuromojiと同梱辞書のライセンスを `licenses/` と `THIRD-PARTY-NOTICES.md` に保存した。

### 14.2 設計から変更した点

**補正のモデル応答**：初期案の候補ID・置換語を直接選ばせる方式だけでは、導入済みGemmaが原文を維持して訂正を見送る例が多かった。実装では、まずJSONの本文として校正案を受け取り、候補位置の標準辞書同音語への最小置換に完全分解できる場合だけ採用する。本文をそのまま採用する経路はない。変更案がなければ、原文を含めた同音語の候補文を最大48件・6,000 UTF-8バイトまで提示し、IDを選ばせる。変更案には類義語の判定も加え、意味の近い語の表記の使い分けは自動訂正しない。複数要求を含め、補正推論全体の期限は3秒に保つ。

**複合語**：標準辞書が「新／札」のように分割する場合に限り、連続した既知の名詞・接頭詞を最大3形態素までまとめ、合成した読みに標準辞書の同音語があるとき候補にできる。任意の句や未知語を補う処理は行わない。

**長文の整形・要約**：4,096トークンの共通設定に収まるよう、入力を1,200 UTF-8バイト以内に分割する。要約は区間別の結果の連結で、全体の再要約は今回実装していない。分割した場合は画面に通知する。

**イベントとデータ形式**：補正結果は `caption.correction` / `translation.correction` の `status` で区別し、終了は `caption.finished` / `translation.finished` とした。訳文は既存互換の文字列フィールドを維持する。古い結果の排除はセッションUUID、行ID、revision、Abortと中断状態の一致で行い、設計案の独立した `inputGeneration` 検証は追加していない。

**モデル更新**：利用者の追加指示に基づき、公式レジストリの `gemma4:latest` と導入済みmanifestが異なることを確認した。別タグでファイルを先行取得し、進行中の録音試験を終えてから通常タグを更新した。起動時の自動ダウンロードは導入していない。照合結果は `reports/gemma-latest-check.json`、更新前の品質・準備確認は `reports/pre-model-update/` に保持する。

### 14.3 評価の解釈と未評価の事項

200例の人工テキスト集合は実装・プロンプト調整にも使った。前置きだけ変えた関連例があり、fixtureに残る `split` 値も未使用のホールドアウトを意味しない。設計第11節で求めた「調整に未使用の最終確認集合」は未達である。回帰試験の補正数を一般の会話の補正率として扱わない。

ブラウザと連続録音の試験は日本語合成音声またはASR確定テキストを模した入力を使用した。実際のGemma・Nemotronを利用するが、利用者の実マイク、騒音、発話者差に対する評価ではない。人の音声による正解文付きCER比較、独立した補正品質集合の評価は残っている。実装と自動検証の完了は、これらの音声品質評価の完了を意味しない。
