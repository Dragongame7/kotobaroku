- 運用条件：GPUなしのWindows端末も利用、同時1会議、会議用マイク1台。重複発話の全文認識は必須外。音声ファイルは標準保存しない。

## 1. 推奨する実装方法

**DGX Spark上のNeMo-Speech.cppへNemotron-3-Diarizationを追加し、ASRが返す単語単位の話者情報を、端末上の文字起こし・補正・ライブ翻訳・保存まで引き継ぐ方式を第一案とする。LLMも同じSpark上のvLLMを利用する。**

新しいPython推論サーバーの導入を前提にせず、NeMo-Speech.cppの統合機能を利用する。端末に導入済みのWindows版 `nemo-speech.exe --version` は `0.2.0` で、`--json model list` に当該モデルと別名 `nemotron-3-diarization` / `nemotron-diar` が登録されていることを実機確認した。これは機能の存在確認であり、標準配備先はSparkのLinux Arm64 CUDA版とする。Sparkでのモデルロード・GPU動作・LLM同居性能は別途検証する。

v1.0の到達点は、**会議の中で「話者1〜8」を区別し、発言を別の人の文章と混ぜずに表示・翻訳できること**。表示名の手動変更も同じ会議内で扱う。音声だけから氏名を自動判定する機能や、別会議に同じ人が参加したことの自動照合は含めない。

| 方式 | 現行構成との相性 | 主な追加作業 | 判断 |
|---|---|---|---|
| SparkのNeMo-Speech.cppへモデル追加 | 既存の音声WebSocket契約とASRモデルを利用できる | Arm64/CUDA検証、遠隔接続、モデル準備、話者別区切り、UI・保存 | **第一案** |
| Transformers / NeMo Speechの独立サービス | 独自の話者活動出力・更新制御を実装しやすい | Python/PyTorch環境、サービス運用、音声時刻の同期、セッション管理 | 第一案で必要な情報や性能が得られない場合の次案 |
| 話者活動を使う複数ストリームASR | 同時発話の認識改善を検討できる | NeMo側での統合、必要ならASR変更、日本語品質、計算量を再評価 | 同時発話中の各人の全文認識が必須の場合に検討 |

標準APIの根拠は [NeMo-Speech.cpp v0.2.0 API](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/docs/api.md)、モデル登録の根拠は [同版モデル索引](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/models/index.json)。

## 2. モデルでできることと、アプリで実装すること

Nemotron-3-Diarizationは最大8話者の話者活動と時間区間を推定するモデルで、ストリーミングに対応する。モデル入力は16 kHz・モノラル。ASR本文の生成とは別の役割を持つ。[公式モデルカード](https://huggingface.co/nvidia/Nemotron-3-Diarization)

| 項目 | 扱い |
|---|---|
| 3〜8人の区別 | モデルの対応範囲に入る。会議用マイク・距離・残響を含む実音声で採否を決める |
| 発言者の表示 | 会議内の匿名話者IDを「話者1」などと表示し、利用者が表示名を変更できるようにする |
| 同じ人の再発言 | 同じ録音セッションの話者キャッシュを維持する。長い沈黙後の再発言を重点検証する |
| 同時発話 | モデル自体は複数話者の同時活動を表せるが、現行ASRと標準WSの単語ラベルだけで二人分の全文や重複区間を得られるとは限らない |
| 日本語会議の品質 | 多言語モデルであることと、このアプリの日本語会議で十分な精度が出ることは別。実測で判断する |
| 話者人数 | 上限8話者。設定人数分の話者を必ず出す仕様ではない。9人以上は対象外とする |

話者活動の検出と、同時発話を含む話者別文字起こしの違いは [NVIDIA公式解説](https://huggingface.co/blog/nvidia/nemotron-diarization)、既存ASRを組み合わせる際の制約は [ASR統合ガイド](https://huggingface.co/nvidia/Nemotron-3-Diarization/blob/main/ASR_INTEGRATION_GUIDE.md)を参照。

次案の具体例として、公式NeMo側にはNemotron 3.5 ASRへ話者活動のマスクを適用する `masked_asr=true` の構成がある。現在のASRモデルを継続できる可能性があるが、C++側の単語への話者付与と同じ処理ではなく、話者ごとのASR状態・計算資源が必要。もう一つの公式例Multitalker Parakeetは英語専用のため、日本語会議の既定置き換えにはしない。

## 3. 現行コードで変更が必要な箇所

| 現行の箇所 | 現在の動作 | v1.0で必要な変更 |
|---|---|---|
| `scripts/setup-asr.mjs` / Spark配備処理 | Windows CUDA版v0.2.0とASRモデルを準備 | 標準利用端末でASR導入を不要にする。Spark向けにモデルとランタイムを準備しリビジョン・ハッシュを記録 |
| `scripts/start.mjs` | ASRモデルだけを指定して起動。既存ASRが応答すれば再利用 | 遠隔利用時は端末のASRを起動せず、Sparkの能力と準備状態を確認する |
| `public/pcm-worklet.js` / `src/audio.ts` | 実際のAudioContextレートでモノラルPCM16を送信。話者付き単語は未要求 | `speaker_diarization` と `word_timestamps` を開始時に要求。リサンプルは既存エンジン内に任せる |
| `server/app.mjs` | 確定イベントから `event.transcript` のみ `translation.enqueue()` へ渡す | `words`・時刻・話者IDを保持して共通の正規化処理へ渡す |
| `server/sentence-buffer.mjs` | 確定文字列を文として連結する | 話者が変わったら前の区間を確定し、異なる話者の本文を一つに連結しない |
| `server/translation.mjs` | 文字列を区切り、補正して翻訳する | 発言・話者・単語との対応を維持。話者交代を区切り理由として追加 |
| `src/translation-types.ts` / `src/corrections.ts` | Captionなどに話者情報がない | 共通の発言メタデータを追加。原文の時刻と補正後テキストを区別 |
| `src/App.tsx` / `src/useLiveTranslation.ts` | 通常画面と翻訳で別々に受信・保存 | 両経路で話者・時刻・会議内表示名を保存し、再読み込み後も復元 |
| `src/LiveTranslation.tsx` / `src/Translation.tsx` | 原文・訳文を表示 | 話者名・時刻を表示。全画面・最新順表示・履歴位置保持を継続 |
| `src/Settings.tsx` / `/api/health` | LLM接続の設定と共通状態 | 独立した音声設定、Spark利用状態、話者機能の能力表示を追加 |
| Sparkゲートウェイ（新規） | 存在しない | 認証、別端末間の同時1会議、音声WS・LLM SSEの中継 |
| 端末の会議保存処理（新規） | 主にブラウザへ保存 | 原文・話者・訳文を端末Nodeで逐次保存し、履歴容量と復元を扱う |

ASR側の実装では、認識と話者分離へ同じリサンプル後の音声を渡している。Node側で音声を再分岐して別々にリサンプルする必要はない。[v0.2.0認識実装](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/src/asr/recognizer.cpp)

モデルの利用条件は索引のOpenMDW 1.1表記と公式配布物で確認し、導入案内・第三者ライセンス一覧に参照先を追記する。

## 4. 音声処理とWebSocket契約

### 4.1 最初に試す起動・要求

以下はPoC用の例。今回の調査では実行していない。Sparkに導入したLinux Arm64版の実行ファイルを使い、既存サービスとは別の未使用ポートで検証する。端末の `findNemo()` が返すWindows版をSparkへコピーする構成ではない。

```bash
# 初回のモデル準備。実装では既存の検証付きモデル取得を利用する。
nemo-speech pull nemotron-3-diarization

# 例：PoC用の8082。既存ASRの調整値も引き継ぐ。
nemo-speech serve --asr-model nemotron-3.5 --diar-model nemotron-3-diarization --asr.diar.preset v3-streaming --device cuda --host 127.0.0.1 --port 8082 --no-ui --read-timeout 3600 --max-upload-mb 1024 --asr.streaming.rnnt_right_context 3 --asr.endpointing.enable=true --asr.batching.state_arena_slots 2
```

ブラウザからは、既存の言語・実際のサンプルレート・句読点・endpointing設定に加えて次を要求する。

```json
{
  "type": "session.update",
  "session": {
    "sample_rate": 48000,
    "language": "ja-JP",
    "automatic_punctuation": true,
    "endpointing_ms": 800,
    "word_timestamps": true,
    "speaker_diarization": true
  }
}
```

48000は入力例で、16000と偽って送らない。現在のAudioContextレートを使う。`max_speaker_count` はv0.2.0の文書で互換用・無視される項目とされているため、「会議は8人」と送れば認識人数を制御できる、というUIにはしない。上限はロードしたモデルの能力として表示する。

### 4.2 確定結果を起点にする

標準WSの確定イベントには `words[]` の各要素として `word`、`start`、`end`、`confidence`、取得できた場合の `speaker` が入る。時刻は秒、話者番号は1始まり。`confidence` はASR側の値であり、話者推定の信頼度として表示しない。[WS送信実装](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/server/http/http_server.cpp)

v1.0の第一案は次の順序とする。

1. ASR未確定本文を先に表示し、話者は「判定待ち」とする。
2. 確定イベントの本文と単語列を対応付け、同じ話者が連続する部分を発言区間にする。
3. 話者交代で直前の組み立て中の区間を確定する。句点がなくても次の話者と連結しない。
4. 同じ話者内では既存の文末判定・時間・長さの上限を使う。
5. 発言区間ごとに日本語補正・翻訳を実行し、話者・時刻を付けて更新する。

`delta` に逐次話者情報や後日のラベル修正イベントがあるとは仮定しない。ASR確定は推定結果を受け取ったという意味で、発言者の正しさを保証するものではない。停止時は既存の `commit` で末尾を確定させる。無音による発話確定のたびにWSを作り直さず、会議全体を一つの話者キャッシュで扱う。

無音なしの長い発話中に交代が起きた場合、本文の部分表示は継続するが、話者別の分割・翻訳はASR確定を待つ可能性がある。これが会議用途で許容できない場合は、話者付きの途中結果や更新を公開するエンジン変更・次案サービスが必要。Node側だけで確定テキストを推測分割して解決しない。

### 4.3 本文の欠落を防ぐ

- 日本語に空白を加える `words.map(...).join(' ')` で本文を作り直さない。確定原文を保持し、単語を原文中の範囲へ対応付けて切り出す。
- 句読点・全角半角・数字整形・英語の空白・日英混在を含めて対応を検証する。曖昧な対応を無理に一つの話者へ割り当てない。
- 単語列と本文が対応しない、単語がない、話者が欠損する場合も原文を落とさず「話者不明」の区間を残す。不明区間を前後の既知話者へ自動吸収しない。
- 同じ確定イベントの再受信や最終commitで、既出の単語や本文を重複追加しない。上流の `event_id` と区間情報を使い、本文が同じという理由だけでは削除しない。

## 5. データ設計と翻訳への受け渡し

Captionへ付加する設計例。これは新しいアプリ内部の型であり、上流APIの形式ではない。

```ts
type SpeakerAttribution = {
  sessionId: string;                  // 録音ごとに新規。別会議の話者1と区別
  speakerId: string | null;            // 例: "spk-1"。欠損はnull
  status: 'pending' | 'assigned' | 'unknown';
  origin: 'nemotron3' | 'manual';
};

type SpeechSpan = {
  utteranceId: string;
  sourceStart: number;                // rawSource中のUTF-16オフセット
  sourceEnd: number;
  audioStart: number;                 // 録音開始からの秒。受信時刻ではない
  audioEnd: number;
  speaker: SpeakerAttribution;
};
```

単語列と区間の根拠は生のASR原文に結び付ける。補正・翻訳後に文字数が変わっても、原文のオフセットや音声時刻をそのまま補正文の文字位置として流用しない。

話者ID・時刻・発言順をLLMに決定させない。補正と翻訳の対象本文は一つの話者の区間とし、必要な前後の会話は話者付きの文脈として渡す。別の人の発言を一人の主張へまとめない。整形・要約でも元発言IDと話者を保持し、氏名や発言者を推測で補わない。

話者表示名は `{sessionId, speakerId}` に対する会議内の辞書で保持する。表示名変更で翻訳を再生成する必要はない。区間の話者割り当てを利用者が修正する場合は、モデルの推定値と手動修正を分け、原文を残す。

保存スキーマは次版へ移行する案（現行2→3）。旧履歴は話者未記録として読み込み、過去の本文を一律に「話者1」へ変換しない。通常画面の原稿・履歴と翻訳履歴の両方を対象にする。既存のコピー・テキスト保存に話者名と時刻を含め、機械的に復元可能なJSON保存も追加候補とする。

## 6. 会議用UIと設定

- 録音前に「話者分離」を選択できるようにする。v1.0の初期値はOFFを提案し、モデル導入・準備完了後に利用者がONにする。
- ライブ翻訳と通常文字起こしで、各発言に話者名と開始時刻を表示する。話者色は補助とし、色だけに依存しない。最大8人でも本文領域を圧迫しない。
- 認識中は「話者判定待ち」、欠損は「話者不明」。画面上のラベルは推定であることが分かるようにする。
- 会議内の話者一覧から「話者1」を「田中」などへ変更できる。別の録音の話者1には適用しない。
- 全画面、Esc解除、最新順、履歴閲覧中の位置保持を引き継ぐ。話者ラベル追加による行高変更でもスクロールを飛ばさない。
- 録音中の話者分離ON/OFF・モデル・接続先変更を禁止する。表示名の変更は可能にする。
- 設定画面の「音声認識・話者分離」には、モデル、ロード状態、上限人数、使用エンジン、設定反映に再起動が必要かを表示する。低水準のcache調整値は通常操作欄に出さない。

LLM設定と音声処理の設定は独立させる。外部vLLM（例 `http://{IPアドレス}:8001/v1`）は引き続き補正・翻訳・要約の接続先であり、話者分離の音声APIの接続先にはしない。

## 7. 計算資源・遅延・長時間運用

### 7.1 開発PCの記録とSparkの評価

現行開発PCでの調査時の実測は **GeForce RTX 3080、VRAM 10,240 MiB、使用中6,888 MiB**。これは補助的な開発環境の記録で、標準利用端末の必要仕様でも、Sparkの追加使用量でもない。標準利用端末にNVIDIA GPUは要求しない。

v0.2.0のモデル索引には `Nemotron-3-Diarization.q8_0.gguf` が107,012,128 bytes（約102 MiB）で登録されている。**ファイルサイズを実行時VRAM使用量とは見なさない。** ASR、話者キャッシュ、演算用バッファ、GemmaのKVキャッシュ、画面描画などを同時に計測する。

Sparkでは128 GBのCPU/GPU共有メモリを、ASR・話者分離・vLLM・OSで使う。LLMのキャッシュ量・文脈長・同時実行を制限し、音声処理との競合を実測する。端末内Gemmaとの同居を標準評価条件にはしない。モデル候補と初期の配備値は技術設計書に記載する。

### 7.2 遅延の見方

公式NeMo側の推奨構成には入力バッファ0.32 / 0.64 / 1.04秒があるが、これは処理・転送・ASR・文末待ち・翻訳を含む表示遅延ではない。[モデルカードの構成表](https://huggingface.co/nvidia/Nemotron-3-Diarization#setting-up-streaming-configuration)

また、NeMo-Speech.cpp v0.2.0の文書に記載されたV3既定値は `chunk=13, right_context=1`（80 ms単位）で、入力待ちは計算上約1.12秒となる。NeMoの1.04秒設定と同一とは扱わない。最初は `v3-streaming` を使って実際の起動ログの有効値を記録し、その後に調整する。プリセットと個別geometry設定は混在させない。[同版モデル説明](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/docs/asr/models.md)、[同版話者設定](https://raw.githubusercontent.com/NVIDIA/NeMo-Speech.cpp/v0.2.0/src/asr/diar/diar_pipeline.h)

計測は「音声入力→本文部分表示」「発話終了→話者付き確定」「話者付き確定→訳文表示」を分ける。ON/OFFで同じ入力音声を使い、初回ウォームアップと定常時を分離する。公開ベンチマークの大量バッチ処理速度を、このPCの会議一本の応答速度に置き換えない。

### 7.3 会議中のライフサイクル

- 会議単位で一つのWSと話者状態を維持する。短い発話ごとのモデル再ロードや話者キャッシュの初期化を行わない。
- 録音の停止・WS切断では会議を終了し、再開時は新しいsessionIdにする。再接続後も同じ声を同じ人物として照合できるとは表示しない。
- 端末内の現行排他に加え、Sparkゲートウェイの利用権で別端末間も同時1会議に制限する。複数会議の同時推論はv1.0に含めない。
- モデルの長さ制限とアプリの制限を区別する。上流には累積音声アップロード量・タイムアウトがあり、長時間録音では実際の入力レートを含めて確認する。無制限録音とは案内しない。
- 現行の比較用音声保持は先頭2分までであり、ライブ翻訳には会議全音声の保存基盤がない。停止後の全会議再推論を標準機能にするには、別途音声保存・容量管理の設計が必要。

## 8. 障害と同時発話の扱い

| 状態 | 方針 |
|---|---|
| モデル未導入・ASRにロードされていない | ONで開始する前に検知。理由と「話者分離なしで開始」を提示し、ONの表示のまま開始しない |
| 稼働中の既存ASRが話者分離非対応 | 単なる `/ready` 成功では再利用可と判定しない。外部・手動起動サービスを勝手に停止しない |
| 個々の単語の話者欠損 | 本文を継続して表示し、該当部分を話者不明にする |
| 同時発話の可能性 | 一人分のASRしか取得できなくてももう一人の発言を生成しない。標準WSだけでは重複を確実に検知・表示できるとは約束しない |
| ASR・CUDAの致命的エラー | 受信済み本文を保存し、既存の停止・エラー経路で知らせる。自動再接続で話者IDを引き継いだように見せない |
| LLM失敗 | 現行と同様に原文を残し、話者・時刻付きで翻訳再試行できるようにする |

同時発話中の各人の全文が必須と分かった場合、第一案の表示調整だけでは解決しない。話者活動を利用する複数ストリームASRなどへ検討を進め、日本語対応・対応モデル・GPU負荷を実証する。[公式ASR統合ガイド](https://huggingface.co/nvidia/Nemotron-3-Diarization/blob/main/ASR_INTEGRATION_GUIDE.md)

## 9. 実装順序と採否判定

| 段階 | 作業 | 次へ進む条件 |
|---|---|---|
| 1. 実機PoC | Sparkの別ポートでモデルをロード。GPUなし端末から日本語3・4・8人の録音を実時間送信。LLM単独・同居も比較 | 話者と本文を取り出せ、Sparkのメモリ・遅延・長時間安定性を把握 |
| 2. 発言データ基盤 | 共通正規化処理、話者交代の区切り、原文範囲、セッションIDを導入 | 他人の本文を結合せず、原文を欠落・重複させない |
| 3. 通常画面・ライブ翻訳 | 話者付き発言を両方の表示とLLM処理に接続 | 同じ入力で両経路の話者・本文が一致。未確定表示と確定分割が破綻しない |
| 4. 設定・保存・利用制御 | 遠隔接続・能力確認、端末間の排他、表示名、端末の逐次保存、履歴移行 | 複数端末・再起動・再読み込み・別録音で誤った利用や人物の引き継ぎがない |
| 5. 会議評価 | 実会議相当音声、60分連続、全画面・複数タブ排他、エラー検証 | 合意した品質と性能基準を満たす。対応条件と制限をREADMEへ記載 |

段階1で短い相づちの誤帰属、8人の取り違え、確定待ちが実用性を損なう場合は、モデルの後処理・設定を比較する。それでも必要条件に届かなければ、方式を独立サービスへ切り替える。標準APIにない話者確信度や重複検出をアプリ側で捏造して埋めない。

## 10. 検証項目と暫定の受け入れ基準

### 10.1 検証音声

日本語を主軸に、英語・日英混在も回帰確認する。3人・4人・8人、順番発話、無音なしの交代、1秒未満の相づち、長い沈黙後の再発言、似た声、遠距離、残響、雑音、笑い、割り込み・同時発話を含める。TTSの模擬会話だけで採用を決めない。

人手の話者・区間・本文の正解を付けた評価用セットと、調整に使うセットを分ける。8話者の代表的な音声が準備できなければ、モデル上限8人とアプリで実証済みの人数を区別して報告する。

### 10.2 指標

- 話者分離単体：DER、話者数の正解率、話者数誤差。重複を含めるか、collar、評価区間、モデル・量子化・設定・ハードウェアを併記する。
- アプリ全体：話者付き本文の正解率、交代境界誤差、短い相づちの誤帰属、IDの取り違え。IDの数字そのものではなく、録音単位で正解話者との最適対応を取って評価する。
- ASR：日本語は文字誤り率、英語は単語誤り率をOFF時と比較する。話者単体のDERが良くても、本文が欠落する構成は採用しない。
- 性能：定常時の各段階のp50/p95遅延、実時間に対する処理速度、GPUピーク使用量、60分間のメモリ推移、停止時の末尾欠落。

標準WSの単語区間をつなげた結果だけでは、重複を含むモデル本来のDERを正確に測れない。モデル単体は独立diarization出力と正解RTTMを用い、話者付き文字起こしの評価と分ける。評価方法は [公式評価ガイド](https://huggingface.co/nvidia/Nemotron-3-Diarization/blob/main/diarization_evaluation.md)を参照。ガイドのログ中の `CER` は話者混同率であり、本アプリで使う日本語の文字誤り率とは別。

### 10.3 暫定の受け入れ基準

以下は公式性能値ではなく、本アプリ向けに提案する基準。PoCで結果を出し、実装着手前に固定する。

1. 異なる既知話者の本文が一つの翻訳入力へ混入しない。分割・補正・保存による原文の欠落と重複がない。
2. 話者分離OFF時は既存の文字起こし・翻訳・補正・全画面操作の回帰検証が成功する。
3. 準備した3〜8人の評価セットで、話者を対応付けた非重複発話の原文文字の帰属正解率90%以上を暫定目標とする。話者不明も誤帰属側に数え、録音別・人数別に併記する。重複部分は別集計する。
4. 発話終了から話者付き確定までのp95遅延増加をOFF比1.5秒以内にすることを暫定目標とする。訳文の遅延は別に記録し、無音なしの交代待ちは別条件で報告する。
5. GPUなしWindows端末とSparkのASR・話者分離・vLLM同居構成で60分を完走し、OOM・切断・累積的な処理遅れを起こさず、停止時の末尾を取り込める。
6. モデル未準備・話者欠損・LLM失敗・再接続で、動作状態や話者IDの継続について誤解させない。
